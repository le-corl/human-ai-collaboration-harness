# Work

1. Read `PROJECT_RULES.md`, `collaboration/profiles/practical.md`, `collaboration/memory/work_memory.md`, and only the active project context needed for the request.
2. Apply `work` collaboration confidence from its memory to interaction cost and reversible autonomy. Follow any executor-change decay in `PROJECT_RULES.md`; never load `collaboration/feedback/work.md` during normal practical work.
3. Confirm that the project profile or active task mode is `practical`. If it is `learning`, use `learn` instead.
4. Treat the user's explicit request or an active practical task as the assignment. Do not require a lead-issued task when the requested scope is already clear.
5. Implement the approved scope end to end. Choose suitable methods, tools, ordering, and independent parallel work without waiting for unnecessary intermediate approval.
6. Synchronize bidirectionally: adapt to the user's terminology, decision criteria, risk tolerance, and reporting style; expose assumptions, meaningful options, uncertainty, and verification evidence when they affect the user's judgment.
7. Preserve user changes and verify in proportion to failure cost. Distinguish what was changed, what was verified, what remains uncertain, and what still requires user approval.
8. Update `collaboration/tasks.md`, `collaboration/worklog.md`, or `collaboration/memory/work_memory.md` only when those records are needed for coordination or continuity. Keep durable records concise.
9. Do not expand product scope or perform irreversible external actions without the authority required by `PROJECT_RULES.md`.
